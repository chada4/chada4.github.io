How I work

Six things that stay true no matter what I'm troubleshooting.

Start with the evidence, not the assumption

I don't need to know the answer before I start looking. I'd rather reproduce the issue and follow what actually happens than guess at what's probably wrong.

Give engineering something to work with

A ticket that just says "it's broken" wastes everyone's time. I try to hand off reproduction steps, findings, and context — not just the original complaint.

Explain the why, not just the fix

People remember whether they understood what happened, not just whether it got fixed. I'd rather take an extra minute to explain than leave someone confused.

Make the next ticket easier

If I solve the same problem twice without writing it down, that's on me. Documentation isn't extra work — it's how the next person doesn't start from zero.

Learn the system, not just the workaround

A workaround gets someone through today. Understanding how the system actually behaves is what lets me catch the next five issues before they become tickets.

Watch for the pattern behind the ticket

One customer's weird issue is a data point. Three customers with the same weird issue is a product conversation. I try to notice the difference and say something.
